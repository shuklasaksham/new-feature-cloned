## PROBLEM 1 — OAuth popup returns but app never advances. CAUSE = (c), a front-end ORIGIN/opener mismatch. (a) and (b) are POSITIVELY RULED OUT.

Exact redirect_uri prod is emitting (from live backend logs):
`https://use-bracket.com/api/connect/{provider}/callback`
e.g. observed verbatim:
- `[connect] figma auth-url issued ... redirect_uri=https://use-bracket.com/api/connect/figma/callback`
- `[connect] gmail auth-url issued ... redirect_uri=https://use-bracket.com/api/connect/gmail/callback`
- `[connect] slack auth-url issued ... redirect_uri=https://use-bracket.com/api/connect/slack/callback`
- `[connect] github auth-url issued ... redirect_uri=https://use-bracket.com/api/connect/github/callback`

### (a) redirect_uri — CORRECT, not the cause
redirect_uri resolves to the LIVE apex domain `https://use-bracket.com`, NOT a preview/cluster host. PUBLIC_BASE_URL is the live apex and matches. Ruled out.

### (b) provider-side redirect registration — REGISTERED, not the cause
The live callbacks succeed end-to-end in prod:
- `GET /api/connect/figma/callback?code=... 200 OK` → `[connect] figma connected → stored under user_id=user_9c7a83e10185`
- `GET /api/connect/gmail/callback?...code=... 200 OK` → `[connect] gmail connected → stored under user_id=...`
Token exchange completing (code accepted, token stored) proves the LIVE `https://use-bracket.com/api/connect/<provider>/callback` IS a registered/authorized redirect URI on Figma/Google/etc. — otherwise the provider would reject with redirect_uri_mismatch before ever issuing a code. Ruled out. (One unrelated benign line seen: `gmail token refresh failed status=400` — expired refresh token for one user, not the connect flow.)

### (c) ROOT CAUSE — the break is purely front-end message delivery across origins
The backend half of OAuth fully succeeds (200 + "connected → stored"), so the only thing left broken is the popup→opener handoff — exactly the "popup returns, nothing happens, no toast" symptom.

All OAuth machinery is hard-bound to the APEX origin `https://use-bracket.com` (both REACT_APP_BACKEND_URL and PUBLIC_BASE_URL). The popup and its callback HTML (which runs `window.opener.postMessage("bracket-oauth:{provider}:ok","*"); window.close()`) therefore ALWAYS run on `https://use-bracket.com`.

But the app can be — and is — loaded on OTHER origins: `www.use-bracket.com` and `design-decided.emergent.host`. When the user opened the app on one of those, the opener document's origin differs from the popup/callback origin (apex). The postMessage is emitted from `use-bracket.com` to an opener on a different origin; the `AddSourceDialog` listener does not accept it (origin check / severed cross-origin opener), so the "load sources" step never fires → nothing happens. This is why it works in PREVIEW (single origin) and fails on LIVE (multi-origin). `x-forwarded-host` is being normalized/overridden to the apex (or falling back to PUBLIC_BASE_URL), so the callback origin never follows the origin the user actually loaded.

### Fix direction for E1 (source/config — pick one, not applied here)
- Preferred: make the OAuth origin follow the origin the user actually loaded — build `_redirect_uri()` from the real request Host (ensure ingress/Cloudflare passes `x-forwarded-host`/`x-forwarded-proto` through, and stop normalizing to apex) so popup+callback share the opener's origin; OR
- Serve the app from a single canonical origin — 301-redirect `www.use-bracket.com` and `design-decided.emergent.host` → `https://use-bracket.com` so the app is only ever loaded on the apex; AND/OR
- Make `AddSourceDialog`'s postMessage listener accept messages from all valid app origins (apex, www, emergent.host) instead of a single origin, and have the callback page post to a known target origin rather than rely on same-origin.
Whichever is chosen, register every callback origin used with each provider.

## PROBLEM 2 — Preview/prod DB "leak". NOT a shared binding. Databases are SEPARATE.
- Prod `DB_NAME` != preview's `bracket_db` (matches_expected=false vs "bracket_db").
- Prod DB actually in use (resolved server-side from prod MONGO_URL): db_name = **`design-decided-bracket_db`** — the platform-namespaced production database, distinct from preview's `bracket_db`.
- Prod `MONGO_URL` is the Emergent-managed Atlas cluster (mongo_query reached it and listed 27 collections there); preview uses a LOCAL mongod. Different host, different connection string, different DB name.
- Conclusion: production and preview are NOT sharing a connection string or DB name — there is no infrastructure-level cross-write. Any apparent cross-visibility is at the application/data level (e.g. the same seeded admin/demo accounts — ADMIN_EMAILS/DEMO_* exist in both — or the same person testing both envs), NOT the DB binding. No action needed on the binding.

Note: the committed complete-user-deletion cascade fix is unrelated to both issues above and safe to ship in the next deploy.
